# PPT Request Guard — Mandatory New-Deck Entry Gate

This file is the fail-closed authority for every **new presentation deck** request.

## Canonical entry routing

For every FriendY new PPT/presentation/slides request:

1. Bind first to project `SLIDE_MASTER` and repository `FriendY0421/slide-master`.
2. A host-required `artifact_handoff` / presentation-preparation call may occur first because the ChatGPT host requires it, but that call is **preparation only**. It is not template selection, not FAH `ALLOW`, and never permission to create a PPTX.
3. Evaluate the FAH Execution Contract before research, project initialization, SVG authoring, or PPTX export.
4. Missing `TEMPLATE_SELECTION` evidence is `WAIT_USER_ACTION` and must stop generation.
5. Upstream `byungjunjang/slide-master`, generic slide generators, host-native artifact shortcuts, or a successful `artifact_handoff` call must not bypass this gate.

**Hard interpretation:** `artifact_handoff = prepare`; valid `template_selection.json = permission to generate`.

## Scalable live template catalog — never hard-code ids or counts

Template discovery is **GitHub-index-driven** from the latest `FriendY0421/slide-master` `main` state.

Canonical catalog sources:

- `.claude/skills/ppt-master/templates/decks/decks_index.json`
- `.claude/skills/ppt-master/templates/layouts/layouts_index.json`
- unified by `.claude/skills/ppt-master/scripts/template_catalog.py`
- stable visual catalog generated by `.claude/skills/ppt-master/scripts/template_gallery_markdown.py`

The committed stable gallery is `docs/template-gallery/README.md`. Adding, updating, or removing a registered Deck/Layout must be reflected by regenerating this catalog and verifying it with `--check`.

Selection keys are collision-safe:

- `deck:<id>`
- `layout:<id>`
- `free`

Existing bare Deck ids remain backward-compatible only when unambiguous.

## Canonical template-selection surface — STABLE VISUAL GALLERY FIRST

The default selection surface is the GitHub-rendered visual catalog at `docs/template-gallery/README.md`.

This surface is intentionally host-independent. It uses normal GitHub Markdown plus the repository's **actual registered SVG previews**, so it does not depend on ChatGPT inline HTML, JavaScript, Canvas, or a temporary localhost server.

For each new PPT request:

1. Recommend only genuinely relevant templates from the live catalog; recommendation never auto-selects.
2. Give the user the stable visual gallery path/link and the recommended selection IDs.
3. The user reviews the representative preview and expandable detail layouts.
4. The user returns an exact `deck:<id>`, `layout:<id>`, or `free` choice in chat.
5. Only then may selection evidence be recorded and deck generation begin.

### Optional richer surfaces

An in-chat native visual gallery or self-contained interactive HTML may be used **only when the current host positively supports it and the assistant can verify that it actually rendered**.

- Host-native visual rendering is a convenience layer, not an execution dependency.
- `template_gallery_inline_html.py` remains available as an optional rich picker.
- `template_gallery_unified.py` remains available for local/external recovery.
- Failure of a richer surface must fall back to the stable GitHub visual catalog without bypassing template selection.

**Never say that a gallery, modal, image, or picker was displayed unless the current turn produced verifiable visible output.**

## Required visible behavior

The stable visual catalog must provide:

1. All currently registered Deck/Layout templates, not a fixed historical list.
2. A real representative preview from each registered workspace.
3. Up to 6 real registered detail layouts for each template.
4. Collision-safe selection IDs.
5. Free Design as an explicit option.
6. No redrawn approximations presented as registered templates.
7. A clear instruction to return the selected ID to chat.

Purpose-aware recommendations remain in the conversation because they depend on the actual PPT request; the catalog itself remains complete and neutral.

## Selection evidence and generation permission

A preview view, link click, recommendation, `artifact_handoff` call, or tentative choice is not selection.

After the user explicitly returns the selected ID in chat, record it through:

`record_template_choice_v2.py <deck:id|layout:id|free> --confirmed --purpose "<purpose>" --output <result.json>`

Then initialize only through:

`new_deck_init.py <project_name> --template-selection-result <result.json>`

Only after this evidence exists may content research/generation begin.

## Fail-closed UI and execution rules

The following are explicit failures and must stop the new-deck pipeline:

- generating PPTX immediately after `artifact_handoff`;
- inventing template names, IDs, screenshots, or previews;
- using a fixed/hard-coded template list that ignores the current GitHub indexes;
- claiming a gallery was displayed when no visible artifact/link was actually produced;
- recording selection before the user explicitly returns a final ID;
- creating/researching the deck while the user is still choosing a template;
- silently defaulting to Free Design;
- treating failure of interactive HTML as permission to skip template selection.

A text-only ID list is allowed only as the last recovery path when the user cannot access any visual surface. In that case explicitly state that visual preview is unavailable; never describe text-only output as a visual gallery.

## Fallback hierarchy

Use these surfaces in this order:

1. **Primary / stable:** GitHub-rendered Markdown visual catalog (`docs/template-gallery/README.md`).
2. **Optional convenience:** conversation-native real registered previews, only when actual visible rendering is verified.
3. **Optional rich picker:** self-contained interactive HTML (`template_gallery_inline_html.py`), only on a positively supported host.
4. **Recovery:** external/local HTML (`template_gallery_unified.py`) when specifically useful.
5. **Last resort:** text selection IDs with an explicit visual-unavailable notice.

No fallback may bypass the explicit user-selection handshake.

## Fail-closed evidence

No valid `template_selection.json` (selected or documented exemption) means the new-deck gate did not pass. `template_gate.py`, `new_deck_init.py`, and guarded `svg_to_pptx.py` remain the downstream enforcement layer.
